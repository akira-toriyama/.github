# Contributing

Conventions shared across the repositories under this account. On commit
messages this file is deliberately thin: since glyph v2 (shipped as tag
v3.0.0) the grammar is not prose anywhere — a commit means what the
repository's own `glyph.toml` says, and glyph's documentation is the
reference. Prose copies of a grammar rot; this file keeps only what is
convention rather than mechanism, and links the mechanism where it lives.

## Commit messages

The engine is [glyph](https://github.com/akira-toriyama/glyph). Every
repository carries a committed `glyph.toml` (generated by `glyph init`,
never hand-written); the first `[[patterns]]` entry that matches decides what
a commit means, CI enforces it on every pull request (the fleet-distributed
`commit-lint.yml` caller runs glyph's reusable `lint.yml`), and release time
consumes the same answer (`glyph release` / `glyph bump` / `glyph notes`).

Read the grammar where it lives — do not reconstruct it from memory or from
this file's history:

- **your repository's `glyph.toml`** — the actual patterns that judge your
  commit, comments included;
- **[glyph's README, "Commit format"](https://github.com/akira-toriyama/glyph#commit-format)**
  — the sigil vocabulary, the 0.x fold, promotion, and everything the pattern
  file can express.

What stays convention here, above any pattern file:

- **The sigil is the version signal, and the only one.** `=` none / `~` patch
  / `^` minor / `!` major / `%` promote to 1.0.0. The gitmoji prefix is for
  the reader and decides nothing. Writing the signal down is the point — a
  sigil-less subject is a violation once a repository's migration window is
  gone.
- **Footers are not parsed.** `BREAKING CHANGE:` / `NON-BREAKING:` are
  retired with the v1 engine; a breaking change is `!` (or `%`) on the
  subject line, nothing else. Trailers like `Co-Authored-By:` are of course
  still fine — they are just text to glyph.
- **Subjects are English**, imperative, lowercase start, no trailing period.
  The body explains the why; a subject-only commit needs no body.
- **A pull-request title is a commit subject.** A squash merge records the PR
  title as the one line that lands on `main`, so the grammar governs it like
  any other subject (glyph's `lint --pr` checks it in the same gate).
  Versioning is immune by construction either way — the bump folds each PR's
  individual commits, never post-squash subjects.
- **Removals must say whether they break anyone** — a `:fire:` / `:coffin:` /
  `:truck:` commit that takes away anything another repo or a user can
  reference carries `!`. The v1 footer-based declaration rule retired with
  footer parsing; the sigil is now the whole declaration, and it is on you,
  not the linter (no commit-message linter can know whether a removed symbol
  was public).

> **Migration state.** Repositories moving from the v1 grammar run a
> v1-acceptance window in their `glyph.toml`: a sigil-less gitmoji subject
> lints clean WITH a warning and folds as none — green and loud is the
> expected state, not a defect. The window is removed per repo once the
> release walk's base sits past its sigil-less history. The v1 grammar
> (gitmoji-as-type driving semver, footer parsing) and the Conventional
> Commits + git-cliff era before it are history, kept only in this file's own
> git log.

## Measured claims in committed documents

A behaviour claim in a committed document is either measured or absent:

- Do not write down how a system behaves unless you ran or reproduced it.
  Inferred, remembered, or "should" behaviour does not ship in docs.
- When you write one, cite the measurement: the test that pins the claim
  (preferred — e.g. glyph's `internal/markdown` package doc names the GitHub
  rendering probes in `markdown_test.go`, and its doctor checks cite
  DESIGN §7), or the command/run that observed it, with the date.

That is the whole rule. Vocabulary bans and lint mechanization were
considered and rejected: they only ever catch yesterday's wrong sentence.

## Release flow

Both release shapes read the same commit data; the difference is only who
builds the artifacts. (**Verdict is glyph's; artifacts are GoReleaser's.**)

- **Rolling-draft repos** (glyph's reusable `release.yml`): every push to
  `main` recomputes the verdict from `lastPublishedTag..HEAD` and converges
  the repo's single **draft** GitHub Release (notes + next `vX.Y.Z`). **No
  tag is created** — review the draft and **Publish** it in the GitHub UI;
  GitHub creates the tag at publish time. A no-bump range means no draft
  (unless the repo's `glyph.toml` sets `draft_on_none = true`, which keeps an
  "Unreleased" placeholder alive instead).
- **Binary-distribution repos** (tag-driven GoReleaser): the next tag comes
  from `glyph bump`, the release notes from `glyph notes`; GoReleaser owns
  the artifacts, checksums, and attestation.

The fleet migration is complete: every releasing repo is on a glyph flavor
above, and the hub's old git-cliff `release.yml` reusable is retired.

## Local hook (optional)

Install once per clone, in any repo:

```sh
glyph hook install
```

That writes the local hooks (`commit-msg` pipes the message into
`glyph lint --stdin`; `pre-push` lints the outgoing range), so a violation
surfaces as you commit rather than after a push. The hooks carry **no copy of
the convention** — they call glyph, which reads the repo's `glyph.toml`, so
they cannot lag the rules. Where glyph is not on `PATH` the hook warns and
lets the commit through: CI is the authority, the hook is only an early
warning.

It honours `core.hooksPath` and refuses to overwrite a hook it did not write
(`--force` overrides). `glyph hook install --print` shows the script without
installing it.
